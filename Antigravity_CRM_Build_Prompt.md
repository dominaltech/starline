## 1. Project Summary

Build a **fully offline, desktop billing + CRM + inventory management software** for a client business named **"Star Line Services"** (Shop No. 3, Anvar Estate, South Sadar Bazar, Lashkar, Solapur — repairs AC, Refrigerator, Washing Machine, Micro Oven & Home Appliances, and issues spare-parts/service invoices, some tied to AMC — Annual Maintenance Contract — work). Beyond this repair/spares business, the product module should still stay generic enough (name, SKU, HSN code, unit, buy price, sell price, image, rack/section, stock qty) to extend to other retail/service/distribution use if needed later, including jobs where **technicians/workers are assigned to on-site installation/repair work** tied to a sold product/service line.

The software must work **100% offline** — no internet dependency for core operation. All data lives in a **local relational (SQL) database** on the machine (SQLite or a local instance of PostgreSQL/MySQL — pick whichever gives the most reliable offline embedded experience for a desktop app; SQLite is preferred for a single-machine desktop deployment unless you're building a LAN multi-terminal setup, in which case a local MySQL/PostgreSQL server is better — please decide and justify the choice before implementation).

Recommended stack (adjust if you have a better offline-first option, but justify the change):
- Desktop shell: Electron / Tauri (Tauri preferred for smaller footprint) or a native app if that's more reliable for the SQL backup/restore requirements.
- Backend/local API layer: Node.js or Python (FastAPI) running locally, talking to local SQL DB.
- DB: SQLite (file-based, easy backup) with a proper relational schema (see Section 8) — normalized tables with foreign keys, not flat JSON blobs.
- Frontend: React (or the framework Antigravity defaults to) with a clean component library, but **no default "AI-generated" look** — follow the visual spec in Section 2 precisely.
- PDF/Image generation: for printable bills and balance sheets (Section 5, 7).

## 3. User Roles & Permissions

Two roles only, both stored in the local DB with hashed passwords (bcrypt/argon2), session-based local login:

**Super Admin**
- Full access.
- Only Super Admin can set/edit **Buy Price** for products.
- Only Super Admin can set/edit **Selling Price** for products.
- Can create/manage Admin accounts.
- Can view all financial reports (balance sheet, profit reports).
- Can access backup/restore settings.

**Admin**
- Can create bills, manage customers, manage stock movement, assign workers to jobs, update job status.
- **Cannot** see or edit Buy Price (cost price) — this must be hidden from the UI entirely for this role, not just disabled.
- Can view Selling Price only (read-only, cannot edit it).
- Can view basic sales list but not profit/margin figures (margin = tied to buy price, so hide anywhere buy price would be inferable, e.g., hide "profit" columns from Admin's view).

Build this as a proper role-based access control (RBAC) layer at both the API and UI level — don't just hide buttons in the frontend while leaving the data reachable from the local API/DB layer.

## 4. Customer Management

- Fields: Name, Mobile Number, Address, and running **Dues/Balance** for that customer (auto-calculated from unpaid bill amounts, updated in real time as bills/payments are recorded).
- **Customer search**: search-as-you-type by Name or Mobile Number, from anywhere a customer needs to be selected (especially the new-bill screen). Implement this as:
  - Debounced live search hitting an indexed local DB query (index the `name` and `mobile` columns).
  - Fuzzy/partial matching (substring + basic typo tolerance, e.g. SQLite `LIKE` with normalization, or a lightweight fuzzy-match library) so partial names/numbers still surface the right customer.
  - Results dropdown shown directly below the name/mobile input box while billing.
- **Duplicate-customer logic (important, described by the client)**:
  - When starting a new bill, as the user types a customer's name or mobile number, the system checks the customers table for an existing match.
  - If a match is found, show it as a selectable suggestion below the input field; selecting it **auto-fills** Name, Mobile, Address, and shows the customer's current Dues.
  - If no match is found and the bill is completed, automatically create a new customer record from the entered details — do not create a duplicate record on the next visit; that visit must match against the existing record instead.
  - Matching should primarily be on mobile number (most reliable unique key) with name as a secondary signal.
- A dedicated **Customer Details page** per customer showing: profile info, full bill history, current dues, and payment history.

## 8. GST Data Export — GSTR-1, GSTR-3B (Excel + JSON)

This is the most important and most technical requirement, directly requested by the client's CA for tax filing. **The exported files must match the GST portal's own offline-tool format exactly**, using the attached GSTR-1/GSTR-3B JSON and Excel files (files 1–4 in Section 0) as the schema source of truth. Do not design your own format — the CA needs to either upload these files directly to the GST portal's offline utility or hand them to their existing filing tool, so structural fidelity matters more than anything else in this section. GST-mode bills from Section 6 (with their CGST/SGST split) are the source data for this export.

### 8.1 How the data maps from the CRM to the export (this is the part we were unsure about — please implement exactly this logic)

The CRM already has, per bill: customer (with GSTIN if the customer is a registered business — add a GSTIN field to the customer record, optional, used only for B2B classification), invoice number, invoice date, place of supply (default to the business's own state, e.g. "27-Maharashtra", unless customer state differs — infer place of supply from GSTIN state code if available), each line item's taxable value, HSN code, tax rate, CGST amount, SGST amount, and whether the bill was GST or Non-GST.

From this, at export time, the software must **classify and aggregate** every bill in the selected period into the GSTR-1/GSTR-3B sections exactly like the attached reference files:

- **B2B** (`b2b` in JSON / `b2b,sez,de` sheet in Excel): every GST bill where the customer has a GSTIN. Group by customer GSTIN, list each invoice with number, date, value, place of supply, reverse charge flag ("N" by default), invoice type ("R" for Regular), and per-item taxable value + CGST/SGST.
- **B2CS** (`b2cs` in JSON / `b2cs` sheet in Excel): all GST bills where the customer has **no** GSTIN (regular retail customers), aggregated by tax rate and place of supply into a single summary line per rate/state combination (not one row per invoice — this section is a rate-wise total, matching the sample file).
- **CDNR** (Credit/Debit Notes for Registered recipients): every stock-return/credit-note created against a B2B (GSTIN-holding) customer — note number, note date, note type ("C" for credit), value, taxable value, tax rate — matching the `cdnr` sheet structure exactly.
- **HSN Summary** (`hsn.hsn_b2b` / `hsn.hsn_b2c` in JSON, `hsn(b2b)`/`hsn(b2c)` sheets in Excel): auto-aggregate every sold line item by HSN code + rate, summing quantity, taxable value, CGST, SGST — split into a B2B HSN table and a B2C HSN table exactly as the sample shows.
- **Documents Issued** (`doc_issue` in JSON / `docs` sheet in Excel): auto-generate the invoice number range (first to last invoice number issued in the period), count of invoices, and count of cancelled invoices; same for credit notes issued in the period.
- **GSTR-3B**: aggregate ALL GST sales in the period into `sup_details.osup_det` (total taxable value, total CGST `camt`, total SGST `samt`) exactly as in the sample JSON/`3B.xlsx`. If the software later tracks purchases/ITC, populate `itc_elg`/`itc_net` the same way (for now, if purchase-side data isn't tracked yet, still generate the section with zeros so the file structure is valid and the CA can fill ITC manually).

### 8.2 Export format decision (this was our other point of confusion — resolve it as follows)
- Provide **both formats as export options**, selectable per export:
  - **JSON**: generate a file byte-for-byte structurally identical to the attached `..._GSTR1_...json` and `..._GSTR3B_...json` (same key names: `gstin`, `fp`/`ret_period`, `b2b`, `b2cs`, `hsn`, `doc_issue`, `sup_details`, `itc_elg`, etc.). This is the format that can be uploaded directly to the GST portal's "Prepare Offline" JSON upload option.
  - **Excel (.xlsx)**: generate a file matching the attached `GSTR1_...xlsx` / `3B.xlsx` sheet layout (same sheet names, header rows, and column order) — this is for the CA's manual review/record-keeping, and can also be converted back to JSON by the GST offline tool if needed.
- The export screen should let the user pick: (a) Return type — GSTR-1 or GSTR-3B, (b) Period — month/quarter picker, (c) Format — JSON, Excel, or both, then generate the file(s) to a local folder.
- Validate the GSTIN of the business is set once in Settings and stamped into every export (`gstin` field), along with the correct return period string format (`MMYYYY`, matching the sample `"062026"`).

## 9. Search — General Requirements Across the App

Wherever a search box appears (customers, products, bill history), implement:
- Debounced live/incremental search (don't wait for Enter).
- Search across multiple relevant fields at once (e.g., product search by name, SKU, or HSN code simultaneously).
- Indexed DB columns for anything searchable, to keep it fast even with thousands of records.
- Recent/frequent items shown when the search box is focused but empty (e.g., recently billed customers/products) to speed up repeat entries.
- Keyboard navigation of search results (arrow keys + Enter to select) for fast billing-counter use.

## 11. Database Requirements

- Proper normalized relational schema in the local SQL database — suggested core tables: `users`, `customers`, `products`, `sections`, `stock_movements`, `credit_notes`, `bills`, `bill_items`, `workers`, `bill_item_status`, `settings`. Use foreign keys and constraints correctly (e.g., `bill_items.product_id -> products.id`, `bills.customer_id -> customers.id`).
- All monetary values stored precisely (avoid floating point rounding issues — use fixed-point/decimal storage).
- All writes should be transactional (e.g., completing a bill must atomically: insert bill + items, decrement stock, update customer dues).
